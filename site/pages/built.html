How this was built

RigReady is built by one developer directing AI coding agents. This page says who did what, how the work is checked before it counts as done, what was tested on real hardware, and what has not been verified yet.

Who did what

Mark Cheli, the developer, owns the project and the rig it was built on. He decided what the product is and what comes first (written down in docs/PRODUCT.md), set the safety rules, agreed what each requirement must do before it was built, looked at the screenshots the tests produce, ran the hardware tests on his own PC, and decides what is released. He did not write the code by hand.

AI coding agents (Anthropic's Claude, working in Claude Code) wrote the code, the tests, the manual and this website, researched the game file formats and the hardware (docs/research), and recorded the evidence for each requirement. Several agents worked at once, each in its own feature folder on its own branch; a branch was merged only after the full check passed.

What stands behind the code is the set of checks below, not a line-by-line human review of every file. If that is not enough for you, the source and the tests are public and you can judge them yourself.

Version 1 of RigReady was built with AI agents too, without these rules. When it was checked in October 2026, its record of what worked was wrong: parts that existed but were not wired up, a button that reported success for something it did not do. Version 2 was rebuilt from scratch around the rules below so that a claim like that cannot be recorded.

What "done" means here

Every requirement is an entry in the requirements ledger with acceptance criteria written before the work. An entry can be marked done only with evidence: the name of a test that exercises the real code path and, for anything on screen, a screenshot from a test run. The build fails if a done entry has no evidence, or if a test or screenshot it names does not exist.

Some tests check the whole codebase rather than one feature, so a new feature is covered the moment it exists:

  • Any write outside RigReady's own folder that does not go through the one class that backs up and journals first fails the build.
  • A "sabotage" test makes the simulated PC accept every change and carry out none, then runs every fix and every action: none may report success.
  • Programs must be started as a program plus a list of arguments; a command line built from text fails the build.
  • Anything tied to the developer's own hardware (a device ID, a serial number, a monitor name) fails the build.
  • Every message between the window and the rest of the app is sent malformed and hostile input, and must refuse it.
  • A visible control with nothing behind it fails the build.

What was tested on real hardware

One rig: a Samsung 49-inch ultrawide, three small USB screens used for aircraft displays, a Dell desk monitor, WinWing devices (joystick, throttle, three display frames, UFC, ICP and cockpit panels), Thrustmaster TPR pedals, a Virpil control panel, a Stream Deck, TrackIR 5 and a Fanatec Podium DD2 wheel base, with DCS World, iRacing, Le Mans Ultimate, BeamNG.drive, Microsoft Flight Simulator 2024 and the Assetto Corsa games installed.

On that PC, as an ordinary user without administrator rights, tests have:

  • read every USB device, game controller, monitor, audio device, running program and the registry values RigReady uses, and checked them against what the app expects;
  • rotated, moved, switched off and changed the refresh rate of the real monitors, including the three USB screens in portrait, and put the layout back exactly as it was;
  • switched the default playback and recording devices, and put them back;
  • read live input from the controllers, and closed a program politely;
  • timed the checklist and the device scan against the real hardware.

Everything that changes game files (bindings, the DCS screen setup, Export.lua, backups and restores, shared setups, the iRacing repair) was tested on recorded copies of that rig's files in a temporary folder, not on the live game files. A second, hand-written test PC with one joystick and one monitor checks that nothing depends on the developer's rig.

Also tested only on recorded data or in automated runs: restoring a Stream Deck backup file by file, and how the taskbar badge, the ready tone and a real press of the global hotkey look and sound. The binding guides were written from general knowledge of the aircraft and have not been reviewed by a pilot. The changelog lists every known limitation of the current version.

Most important of all: it has been used on one rig. Reports from other hardware are what it needs most, through the hardware report form.

How contributions are reviewed

A pull request goes through the same checks as the developer's own work: the full check and the scenario tests on Windows, a ledger entry with its evidence, and a screenshot for anything on screen. Then the developer reads it against the safety rules before it is merged. Contributions written with an AI tool are welcome if they say so and their author can explain every change. The contributing guide has the details.

How the app protects your PC, and how to report a security problem privately, is on the security page.
